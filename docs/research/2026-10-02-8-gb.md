# Qwen-Image-2.1 на 8 ГБ: GGUF, энкодер по блоку, KV-кэш в ОЗУ

Дата: 2026-10-02. Машина: ноутбук с RTX 4060 Laptop 8 ГБ (для PyTorch
свободно 6.9 ГиБ: остальное держат драйвер и рабочий стол), 23.5 ГиБ ОЗУ
(свободно около 15), Core Ultra 5 125H, Windows 10, драйвер 565.90.

Исходное состояние: проект собран под RTX 3090 (24 ГБ). На этой машине
загрузка шла 47 с, закрепление памяти падало, а первый же выбор Turbo
обрывался нехваткой видеопамяти: INT8-трансформер 6.8 ГиБ на карте плюс
адаптер 1.3 ГиБ.

Заказчик прислал рекомендацию для ComfyUI (GGUF Q4_K_M, энкодер Comfy w4a8 на
процессоре, `--lowvram`, тайловый VAE, KV-кэш на процессоре в int8). Задача —
встроить то же в проект, не трогая путь для мощных карт.

## Что взято из рекомендации, что заменено и почему

| рекомендация | решение | почему |
|---|---|---|
| GGUF Q4_K_M от leejet | GGUF Q4_K_M от **Unsloth** | у leejet нет Q4_K_M (только Q4_K/Q4_0 и т. д.); у Unsloth — полный ряд Q3_K_M…Q8_0 и проверенная раскладка смешанных типов |
| энкодер `qwen3vl_8b_w4a8` (Comfy) | свой INT8 по группам 128, собранный из bf16-весов | w4a8 Comfy — 4-битный кодбук с поворотом активаций (`convrot`) и int8-активациями; формат не описан, и воспроизводить его вслепую — гадать о точности. Свой — измерен (ниже) |
| энкодер на процессоре | энкодер на **видеокарте по одному блоку** | на процессоре 8B-модель — десятки секунд на промт с картинкой; по блоку — 2–4 с |
| `--lowvram` | политика `STREAM`: трансформер резидентен, энкодер по блоку | то же назначение, своё устройство (`residency.py`) |
| тайловый VAE | был и раньше; плитка 384 вместо 512 | пик декодирования −0.7 ГиБ |
| KV-кэш на процессоре, int8 | KV-кэш в ОЗУ, bf16, только крупный | 2 ГиБ по шине за шаг — ~0.3 с из 4; int8 — лишняя ошибка без нужды |
| Turbo GGUF (Abiray, 4 шага) | тот же дистиллят Viggle v0.2.1, **LoRA ранга 128** | проект уже настроен на v0.2.1 (6 шагов, свои сигмы); LoRA r128 — 0.63 ГБ против 1.3, без второго трансформера в памяти |

## Опыт 1. Энкодер в int8: какая схема

`tools/experiments/lowvram_te_sensitivity.py`. Эталон — fp32 (веса и
вычисления в float32, энкодер подаётся по блоку). Сжатие имитируется в
момент подъёма блока, арифметика — как у `quant.Int8Linear`. Ячейка:
средний косинус по токенам / худший токен / относительная ошибка всего
промта. Промты: короткий, с надписью, правка с картинкой 1024².

| вариант | короткий | с надписью | правка |
|---|---|---|---|
| **bf16** к fp32 | 0.99759 / 0.969 / 0.061 | 0.99838 / 0.919 / 0.051 | 0.90328 / 0.010 / 0.456 |
| int8 по строкам к fp32 | 0.98627 / 0.845 / 0.153 | 0.99407 / 0.795 / 0.106 | 0.89786 / 0.010 / 0.470 |
| **int8 по группам 128** к fp32 | 0.99570 / 0.949 / 0.083 | 0.99827 / 0.936 / 0.055 | 0.90155 / −0.022 / 0.457 |
| int8 по группам 64 к fp32 | 0.99402 / 0.924 / 0.096 | 0.99867 / 0.951 / 0.047 | 0.90299 / −0.005 / 0.453 |
| по строкам, кроме `down_proj` | 0.99234 / 0.912 / 0.113 | 0.99763 / 0.943 / 0.065 | 0.90121 / 0.020 / 0.460 |
| по строкам, кроме слоёв 0–3 | 0.98793 / 0.867 / 0.142 | 0.99495 / 0.858 / 0.096 | 0.89930 / 0.014 / 0.467 |

Выводы:

* сам bf16 далёк от точного ответа: 5–6 % на тексте и 46 % на промте с
  картинкой (худший токен — косинус 0.01). Модель с таким шумом обучена и
  работает — значит, мерить сжатие надо относительно этого пола;
* масштаб на строку удваивает шум; главный виновник — `down_proj`;
* масштаб на группу из 128 входов — ошибка на уровне самого bf16. Группа 64
  не лучше. Выбрана 128 (масштабы — 3 % к объёму).

Проверка настоящей сборки (`tools/experiments/lowvram_text_encoder.py`,
int8 g128 к bf16): косинус 0.998 / 0.999 / 0.993, относительная ошибка 6.1 /
4.4 / 11.9 %. Сборка — 21 с на карте, 8.4 ГиБ на диске; кодирование по
блоку — 1.9–3.9 с (первое, по холодному диску, — до 7 с) против 4.2–8.3 с у
bf16 по блоку.

## Опыт 2. GGUF: имена и порядок половин

Файлы GGUF собраны конвертером ComfyUI: префикс `model.diffusion_model.` и
слитый вход SwiGLU `img_mlp.gate_up` (24576 × 4096). Строки квантованного
тензора независимы, поэтому он режется пополам по строкам без пересжатия.
Порядок сверен с INT8-весами Unsloth (имена diffusers): первая половина ~
`gate_layer` с косинусом 1.00 и ~`proj` с 0.00, вторая — наоборот, на блоках
0, 5 и 31. Ошибка Q4_K к INT8 на `to_q` — 4–8 %, ожидаемо для 4 бит.

Загрузка Q4_K_M прямо на карту — 9.5 с, 3.92 ГиБ.

## Опыт 3. Память процесса на Windows

Первая сборка держала 31 ГБ «выделенной» памяти процесса при свободных
3.7 ГБ физической. Разбор по этапам:

| причина | объём | лечение |
|---|---|---|
| пустые `Int8Linear` создавались настоящими тензорами до замены весами; освобождённое куча Windows процессу не вернула | 7.7 ГБ | слои создаются на `meta` |
| GGUF копировался в ОЗУ (`ndarray.copy()`) перед отправкой на карту | 4 ГБ | при загрузке на карту — прямо из отображения файла |
| `safetensors.load_file` отображает файл с копированием при записи: Windows резервирует под весь файл частную память | 8.4 ГБ резерва (не физической памяти) | своё чтение — отображение только для чтения (`text_encoder.read_mapped`) |
| **WDDM**: каждое выделение видеопамяти резервирует столько же выделенной памяти процесса — на случай вытеснения | = видеопамять | неустранимо; физическую память не занимает (рабочий набор не растёт) |

## Опыт 4. Где пик видеопамяти

После загрузки на карте 4.55 ГиБ: трансформер 3.92 + VAE 0.63. Дальше:

* шаги денойзинга 1024² добавляют всего ~0.7 ГиБ;
* **декодирование VAE** плитками 512 — +1.67 ГиБ: это пик денойзинга;
* **кодирование промта** — +1.5 ГиБ даже на коротком промте (таблица
  вложений 0.64 и VAE 0.63, который в этот момент простаивает).

Без лечения резерв аллокатора доходил до 8.4 ГиБ — больше физической
памяти: драйвер Windows молча подставлял общую системную память (медленно).
Ограничение аллокатора физическим объёмом (`set_per_process_memory_fraction`)
это подтвердило — с ним всё падало нехваткой памяти уже на кодировании.

Лечение:

* таблица вложений энкодера остаётся в ОЗУ, строки ищутся на процессоре
  (`Int8Embedding` считает там, где лежит, `StreamedModule(host_modules=…)`);
* VAE на время кодирования уходит в ОЗУ (`ResidencyManager` при `STREAM`);
* плитка VAE 384 (`tools/experiments/lowvram_vae_tile.py`): на настоящем
  кадре 1024² расхождение с цельным декодированием —

  | плитка | пик, +ГиБ | среднее, уровней | худший столбец | худшая строка |
  |---|---|---|---|---|
  | 512 | 1.67 | 1.27 | 2.72 | 2.46 |
  | **384** | **0.95** | 1.89 | 3.99 | 4.26 |
  | 256 | 0.43 | 3.33 | 8.91 | 9.37 |

  256 уже даёт полосы; 384 — компромисс.

системную.

Жёсткий потолок аллокатора физическим объёмом проверен и **отвергнут**: из-за
фрагментации ~0.5 ГиБ резерва не используется, и правка, референсы и 1536²
с ним падают нехваткой памяти; Turbo быстрее не становится (33.8 с против
31.9). Без потолка рабочий пик (≤ 6.5 ГиБ) помещается в карту, а подкачка
драйвера остаётся страховкой на редкие выбросы.

верна, правка «зимний вечер» сохраняет трамвай и надпись. Второй
«референс» в опыте `refs2` — значок «+» из интерфейса; этот прогон — замер
памяти и времени, а не качества.

## Опыт 5. Turbo4: 4-шаговый дистиллят Abiray

`tools/experiments/lowvram_turbo4.py`. `Abiray/Qwen-Image-2.1-viggle-4-steps-turbo-GGUF`,
Q4_K_M (4.19 ГБ) — по карточке, конвертация предварительной версии v0.1
дистиллята Viggle, влитого в трансформер. Правила карточки: 4 или 8 шагов,
CFG 1, без негатива, Euler, расписание «simple» — здесь равномерные узлы
`linspace(1, 1/n, n)` со сдвигом пайплайна и планировщик turbo Viggle
(`shift_terminal: null`). Имена тензоров — те же, что у Unsloth (ComfyUI):
загрузчик `engine/gguf.py` подошёл без правок.

Одни промты и сид (7), кадр 1024², секунды на кадр (новый промт / повтор):

| вариант | плакат | портрет | еда | правка | пик, ГиБ |
|---|---|---|---|---|---|
| LowQuality, 16 шагов | 74.7 / 62.8 | 65.6 / 62.1 | 64.3 / 62.0 | 78.5 / 73.8 | 5.57 |
| Turbo, 6 шагов (r128) | 30.4 / 29.0 | 28.9 / 28.7 | 28.8 / 28.7 | 35.9 / 36.0 | 6.26 |
| **Turbo4, 4 шага** | 26.3 / **19.2** | 22.0 / **19.3** | 21.2 / **19.3** | 29.1 / 25.1 | 5.67 |
| Turbo4, 8 шагов | 33.1 / 33.2 | 33.1 / 33.2 | 33.7 / 33.2 | 41.9 / 41.6 | 5.87 |

На глаз (`logs/turbo4/sheet.jpg`):

* надпись «LISBOA 1934» Turbo4 написал верно и на 4, и на 8 шагах; Turbo
  на этом сиде ошибся («1O34»);
* картинка контрастнее, с выраженной фактурой («HDR»); портрет решён
  иначе — рыбак смотрит в камеру, а не чинит сеть;
* **правка — заметно хуже**: кадр сдвинут, справа появилась стена, сцена
  уходит от исходника. Совпадает с оговоркой карточки (v0.1, «сложные
  правки — с большим разбросом») и с замером самих Viggle: их слитый
  6-шаговый Q4_K_M «заметно уплывает» на 23–29 запросах из 96;
* 8 шагов почти ничего не добавляют и медленнее Turbo.

Решение: пресет **Turbo4** (4 шага, 1024²) рядом с Turbo, не вместо.
Отдельный трансформер подменяется `ResidencyManager.replace_transformer`:
на 24 ГБ основной откладывается на хост, на 8 ГБ отпускается и читается
заново. Сквозной прогон через `Studio` (LowQuality → Turbo → Turbo4 ×2 →
правка на Turbo4 → LowQuality → Turbo): переход на Turbo4 — +3.8 с, возврат —
столько же; Turbo после возврата сам подключает адаптер заново.

## Что не сделано и почему

* **Подача трансформера по блоку** (тогда на 8 ГБ поместились бы Q6_K и
  Q8_0): шаг 1024² на этой карте ~3.5 с, а блок Q8_0 по шине — ~25 мс, то
  есть подача почти бесплатна при упреждающей загрузке. Мешает ОЗУ: Q8_0
  7.1 ГБ плюс энкодер 8.4 ГБ на машине со свободными 15. Рычаг для машин с
  32 ГБ — следующий шаг, если понадобится.
* **Упреждающая подача блоков энкодера** на отдельном потоке CUDA: выиграла
  бы ~1 с на промахе кэша эмбеддингов. Мало по сравнению с минутой
  генерации.
